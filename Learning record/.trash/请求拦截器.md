
请求拦截器（Request Interceptor）就像是所有网络请求发往服务器之前必须经过的**“统一安检站”**。

在企业级项目中，我们之所以要设置这个安检站，就是为了把那些**每次发请求都要做的重复性工作**集中到一起处理。

一般来说，在请求拦截器中我们主要会写以下 **4 类核心业务逻辑**：

### 1. 注入认证凭证 (携带 Token)

这是请求拦截器最基本、也是最重要的工作。 当用户登录成功后，前端通常会拿到一个 Token 并存在本地（如 `localStorage` 或全局状态管理库中）。在拦截器里，我们要把这个 Token 提取出来，并统一塞进请求头（Headers）的 `Authorization` 字段里，这样就不用在每次调用接口时手动传 Token 了。

### 2. 控制全局 Loading 状态

为了提升用户体验，防止用户在等待数据时面对一个“死机”的白屏，我们通常会在请求发起时开启一个全局的加载提示。 比如调用 UI 组件库的 Loading 服务，或者在页面顶部显示一个类似于 NProgress 的进度条。

### 3. 请求参数的清洗与转换

有时候前端组件传递过来的数据不够“干净”，或者不符合后端的标准。

- **过滤空值：** 遍历 `params` 或 `data`，把里面值为 `null`、`undefined` 或空字符串的字段删掉，减少不必要的数据传输。
    
- **序列化：** 对于某些要求传统表单格式的旧版后端接口，在这里将 JSON 对象统一转换为 `x-www-form-urlencoded` 格式。
    

### 4. 防止重复请求 (防抖/取消请求)

如果用户因为手抖或网络卡顿，连续疯狂点击了“提交”按钮，前端就会瞬间发出几十个相同的请求，这不仅浪费服务器资源，还可能导致数据库产生重复数据。 在高级封装中，我们会在请求拦截器里记录当前正在发出的请求，如果发现有完全相同的请求还没回来，就直接拦截并取消掉后面多余的请求。
