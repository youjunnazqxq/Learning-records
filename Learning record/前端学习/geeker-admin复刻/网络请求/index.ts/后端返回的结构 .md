这是一个非常好的切入点！搞清楚 **“后端给我的是什么”**，是写好响应拦截器的前提。

在现代的前后端分离开发（尤其是你参考的 Geeker-Admin 这种标准项目）中，后端返回的数据格式通常是非常**标准化**的。

我们可以把它看作是一个 **“标准三件套”**。

### 1. 标准后端返回结构 (JSON)

不管你请求的是“登录”、“获取列表”还是“删除用户”，后端返回的 JSON 数据结构通常都长这样：

JSON

```
{
  "code": 200,          // 1. 业务状态码
  "msg": "操作成功",    // 2. 提示信息
  "data": { ... }       // 3. 真正的数据 (可能是对象，也能是数组，也可能是 null)
}
```

我们逐个拆解这“三件套”：

#### A. `code` (业务状态码)

- **注意**：这**不是** HTTP 状态码（HTTP 状态码是 200, 404, 500 这些，由浏览器和网关控制）。
    
- 这是**后端程序员自己定义**的逻辑状态。
    
- **例子**：
    
    - `200`: 成功。
        
    - `401`: 未登录/Token过期（虽然 HTTP 可能是 200，但业务上算失败）。
        
    - `500`: 服务器内部报错。
        
- **拦截器怎么用它？**：拦截器会先看这个 `code`。如果不是 `200`，说明业务出错了，拦截器直接报错，不再往下走。
    

#### B. `msg` (提示消息)

- **作用**：给用户看的提示文字。
    
- **例子**："登录成功"、"密码错误"、"用户名已存在"。
    
- **拦截器怎么用它？**：如果有报错（code != 200），拦截器会直接把这个 `msg` 弹窗显示出来（`ElMessage.error(msg)`）。
    

#### C. `data` (真实数据)

- **作用**：前端真正想要的“干货”。
    
- **变化**：它的格式是多变的。
    
    - 登录成功时：它是 `{ token: "..." }`
        
    - 查列表时：它是 `[{ name: "A" }, { name: "B" }]`
        
    - 操作失败时：它可能是 `null`。
        

---

### 2. Axios 包裹层 (外面的快递盒)

需要特别注意的是，**Axios** 会在后端返回的这个“三件套”外面，再包一层它自己的“快递盒”。

当你拿到 `response` 对象时，它是这样的：

JavaScript

```
// 这是 axios 也就是 interceptors.response.use((response) => ...) 拿到的东西
{
  // 👇 Axios 提供的 HTTP 信息
  status: 200, 
  statusText: "OK",
  headers: { ... },
  config: { ... },

  // 👇 这才是后端返回的“三件套”！都在 data 属性里！
  data: {
    code: 200,
    msg: "操作成功",
    data: { 
      username: "Geeker",
      age: 18
    }
  }
}
```

**响应拦截器的核心任务：**

就是把外面那层无用的 `status`, `headers`, `config` 剥掉，直接把里面的 `data`（包含 code/msg/data 的对象）返回给页面。

---

### 3. 在 TypeScript 中的定义

为了让 TS 认识这个结构，我们需要定义一个接口。

请看你的项目文件 `src/api/interface/index.ts`（或者类似的路径），通常会有这样一个通用的接口定义：

TypeScript

```
// 泛型 T 代表那个多变的 data 到底是啥类型
export interface ResultData<T = any> {
  code: number;
  msg: string;
  data: T;
}
```

这就是为什么我们在 `api/index.ts` 里写 `get<T>` 的时候返回的是 `Promise<ResultData<T>>`。

意思是：**“我承诺，这个请求回来后，会给你一个包含 code, msg 和具体数据 T 的对象。”**

---

### 总结

后端返回的形式就是：**`{ code, msg, data }`**。

明白了这一点，接下来的响应拦截器逻辑就非常顺畅了：

1. 解构出 `response.data`。
    
2. 检查 `data.code` 是不是 200。
    
3. 是 200 -> 返回 `data.data` (或者整个 `data`，看项目约定)。
    
4. 不是 200 -> 报错。
